# Design Document: Flaky Property Test Fixes

## Overview

This design addresses the flaky property-based test `should preserve all comments during formatting [source-preserving]` in `formatting-preservation.prop.test.ts`. The root cause is that the `arbitrary_trailing_comment()` generator can produce comments with trailing whitespace, which the formatter legitimately strips, causing the test to fail when comparing comment content.

The fix involves modifying the generator to not produce trailing whitespace in comments, ensuring the test inputs match the expected formatter behavior.

## Architecture

The fix is localized to the test infrastructure:

```
tests/property/generators/primitives.ts
└── arbitrary_trailing_comment() - Modified to not produce trailing whitespace

tests/property/formatting-preservation.prop.test.ts
└── Comment comparison logic - No changes needed if generator is fixed
```

## Components and Interfaces

### Modified Component: `arbitrary_trailing_comment()`

**Location:** `tests/property/generators/primitives.ts`

**Current Implementation:**
```typescript
export function arbitrary_trailing_comment(): fc.Arbitrary<string> {
  const my_comment_text = fc.stringMatching(/^[a-zA-Z0-9 _-]*$/);

  return fc.oneof(
    my_comment_text.map((my_text) => `// ${my_text}`),
    my_comment_text.map((my_text) => `/* ${my_text} */`)
  );
}
```

**Problem:** The regex `/^[a-zA-Z0-9 _-]*$/` allows spaces, which can appear at the end of the generated text. When combined with the comment prefix, this creates comments like `"// text "` with trailing whitespace.

**Solution:** Trim the generated text to remove any trailing whitespace:
```typescript
export function arbitrary_trailing_comment(): fc.Arbitrary<string> {
  const my_comment_text = fc.stringMatching(/^[a-zA-Z0-9 _-]*$/);

  return fc.oneof(
    my_comment_text.map((my_text) => `// ${my_text.trimEnd()}`),
    my_comment_text.map((my_text) => `/* ${my_text.trimEnd()} */`)
  );
}
```

This ensures:
1. Comments never have trailing whitespace after the text
2. The formatter's whitespace normalization doesn't change the comment content
3. The test comparison succeeds

## Data Models

No changes to data models are required. The fix is purely in the test generator.

## Correctness Properties

*A property is a characteristic or behavior that should hold true across all valid executions of a system—essentially, a formal statement about what the system should do. Properties serve as the bridge between human-readable specifications and machine-verifiable correctness guarantees.*

### Property 1: Generated Comments Have No Trailing Whitespace

*For any* comment generated by `arbitrary_trailing_comment()`, the comment text (excluding the comment delimiters) should not end with whitespace characters.

**Validates: Requirements 1.1, 1.2, 1.3**

### Property 2: Generated Comments Are Valid Stata Comments

*For any* comment generated by `arbitrary_trailing_comment()`, the lexer should tokenize it as a valid comment token.

**Validates: Requirements 1.4**

## Error Handling

No error handling changes are required. The fix is a simple modification to the generator that prevents invalid test inputs.

## Testing Strategy

### Unit Tests

The existing `formatting-preservation.prop.test.ts` test will serve as the primary validation:
- After the fix, `should preserve all comments during formatting [source-preserving]` should pass consistently

### Property Tests

The fix itself can be validated by the existing property test infrastructure:
- The `arbitrary_trailing_comment()` generator will be exercised by the formatting preservation test
- If the generator produces comments with trailing whitespace, the test will fail

### Verification Steps

1. Run `bun test tests/property/formatting-preservation.prop.test.ts` multiple times
2. Verify all tests pass consistently
3. Confirm the `valid-block-terminators.prop.test.ts` and `orphan-closing-brace.prop.test.ts` tests continue to pass (no changes needed)
